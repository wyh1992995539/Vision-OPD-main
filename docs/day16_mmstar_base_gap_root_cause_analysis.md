# Day 16：本地 Base 模型 MMStar 论文差距根因分析

## 1. 结论

当前结果已经保留，原始 R3、R4 与 max-token 诊断产物均未被覆盖。本次分析只读取冻结文件，并在独立目录生成机器可读报告与 SHA256。

不能依据 R4 的 `68.00%` 直接断言本地 Base 模型没有复现论文。R4 修复了官方公开评测代码中“抓取回答里第一个大写字母”的答案解析缺陷，因此它是更可信的本地内部指标，但已经不是与论文 Table 2 完全同协议的分数。

现有证据支持以下判断：

1. **解析协议不同是最大的已证实差异。** R3 使用与官方公开代码一致的首字母解析逻辑，MMStar 为 `1126/1500 = 75.07%`；R4 修复解析后为 `1020/1500 = 68.00%`。两者相差 `106` 个净正确样本，即 `7.07 pp`。
2. **1024 token 截断确实伤害结果，但不是唯一原因。** 对全部 163 条截断样本逐级提高上限，并仅重跑上一档仍截断的样本后，最终混合总分为 `1091/1500 = 72.73%`，恢复 `4.73 pp`，仍低于论文 `78.53%`。
3. **Judge 模型不一致会影响论文协议分数。** 论文使用 GPT-OSS-120B Judge，本地使用冻结 Qwen3.5-4B Base Judge。R3 中有 `988/1500` 条进入 Judge，Judge 替换对 R3/论文式结果可能产生数个百分点影响，但目前没有论文逐样本 Judge 输出，无法精确计算。
4. **论文没有给出可核验的 Base 权重 revision/hash 和完整服务运行时。** 本地 checkpoint 已冻结到确切 revision 与权重 SHA256，但无法证明它与论文运行使用的字节完全相同。
5. **当前没有发现 MMStar 数据转换或提示构造错误。** 数据集 revision、1500 条样本、原始问题文本、标签和单图 user 消息结构均与官方公开准备和推理代码一致。论文没有发布数据文件哈希，因此只能判为低风险，不能做字节级证明。

因此，应同时保留两条指标线：

- **R4 修正版**：用于本项目内部比较 Base、Vision-OPD、Cached 和后续模型，避免错误答案被解析器虚增为正确。
- **论文复现线**：另建实验，严格采用官方公开解析器、官方生成默认值和论文 Judge，并明确标注实际可用的替代项。不得覆盖 R4。

## 3. 三种分数的含义

| 分数 | 正确数 | 准确率 | 相对论文 | 可解释含义 |
|---|---:|---:|---:|---|
| 论文 Base | 约 1178/1500 | 78.53% | 0 | Table 2 报告值，无逐样本结果 |
| 本地 R3 | 1126/1500 | 75.07% | -3.46 pp | 官方式首字母解析 + 本地 4B Judge + 1024 token |
| 本地 R4 | 1020/1500 | 68.00% | -10.53 pp | 修正后的确定性选项解析 + 本地 4B Judge + 同一批 1024-token 输出 |
| R4 2048/4096 反事实 | 1072/1500 | 71.47% | -7.06 pp | 仅重跑原 163 条截断样本后的诊断值 |
| R4 自适应 131K 收口 | 1091/1500 | 72.73% | -5.80 pp | 逐级只重跑残留截断；162条自然停止，1条确认为生成退化并计错 |

论文 78.53% 是保留两位小数的汇总值，所以表中的“约 1178”只是按 1500 条换算，不是论文发布的逐样本正确数。

## 4. R3 为什么比 R4 高 7.07 pp

R4 对 1500 条样本的路由为：

- 明确选项正确：994 条；
- 明确选项错误：339 条；
- 无法可靠解析，进入 Judge：167 条。

R3 使用官方公开 `extract_first_option` 逻辑，会在找不到规范选项时退回到回答中的任意第一个大写字母。例如参考答案是 A，而模型末尾明确回答 D 的文本 `Final Answer: D`，旧逻辑可能抓取 `Answer` 的 A 并判对。

全量 R3→R4 迁移矩阵：

| 迁移 | 条数 |
|---|---:|
| R3 对 → R4 对 | 1010 |
| R3 对 → R4 错 | 116 |
| R3 错 → R4 对 | 10 |
| R3 错 → R4 错 | 364 |

116 条“对→错”可进一步解释为：

- 93 条：R4 已明确解析为错误选项，但 R3 首字母规则直接判对；
- 19 条：R4 判为歧义并交给 Judge 判错，而 R3 首字母规则直接判对；
- 4 条：R4 已明确解析为错误选项，但 R3 的本地 Judge 返回 Yes。

10 条“错→对”全部属于 R4 已明确解析为正确选项，但 R3 路由给 Judge 后被判错。

这说明 R3 的 75.07% 含有明显的规则虚高；R4 的 68.00% 更适合作为本地真实性能指标。与此同时，官方公开仓库目前仍保留相同的首字母回退逻辑，所以 R4 不能被标成“与论文 Table 2 完全同协议”。论文实际生成 Table 2 时是否使用了公开代码的这个具体版本，没有逐样本记录可验证。

## 5. token 上限影响

本地冻结协议把评测 `max_tokens` 设为 1024。官方仓库 `official/main` 的 `eval/run_eval.sh` 默认值是 32768；其底层 `infer.py` CLI 默认值是 4096。官方 `run_eval.sh` 的 32768 默认值从该脚本首个提交就存在。

论文正文没有明确披露评测生成上限，因此可以确认的是“本地与当前官方公开复现命令不一致”，不能据此证明论文 Table 2 实际一定使用了 32768。

对 163 条 `finish_reason=length` 的 MMStar 样本做受控重跑：

| 阶段 | 截断子集正确 | 反事实全量正确 | 反事实全量准确率 | 仍截断 |
|---|---:|---:|---:|---:|
| 原 1024 | 20/163 | 1020/1500 | 68.00% | 163 |
| 2048 | 65/163 | 1065/1500 | 71.00% | 83 |
| 2048 + 剩余样本 4096 | 72/163 | 1072/1500 | 71.47% | 46 |

在当时冻结 Gate 下，最后 46 条中已有 4 条正确；即使假设其余 42 条全部因继续提高上限而变对，受控上界也只有 `1114/1500 = 74.27%`，仍低于论文容差下限 `76.53%`，因此当时停止完整 1,500 条重跑的决定合理。

后续按专项修复要求继续对残留样本自适应提高上限，结果如下：

| 上限阶段 | 请求数 | 阶段后仍截断 | 混合总正确 | 混合准确率 |
|---:|---:|---:|---:|---:|
| 8,192 | 46 | 21 | 1,086 | 72.40% |
| 16,384 | 21 | 7 | 1,089 | 72.60% |
| 32,768 | 7 | 3 | 1,091 | 72.73% |
| 65,536 | 3 | 1 | 1,091 | 72.73% |
| 131,072 | 1 | 1 | 1,091 | 72.73% |

最后一条 131,072-token 输出的规范化段落重复率为98.58%，没有产生最终选项，R4 无法解析且冻结 Judge 返回 No。它被保留为原始 `length` 证据并以 `terminal_generation_degeneracy` 计错；收口结果的 `unresolved_output_cap_count=0`。详细凭据见 `docs/day16_mmstar_base_output_cap_repair_brief.md`。

## 6. 类别证据：截断不是唯一问题

| MMStar 一级类别 | R4 准确率 | 1024 截断率 | 仅非截断样本准确率 |
|---|---:|---:|---:|
| coarse perception | 69.60% | 1.20% | 69.64% |
| fine-grained perception | 64.80% | 4.00% | 66.25% |
| instance reasoning | 71.20% | 6.40% | 75.21% |
| logical reasoning | 76.40% | 10.00% | 84.00% |
| math | 78.40% | 19.20% | 95.05% |
| science & technology | 47.60% | 24.40% | 59.26% |

数学和科技类别的截断明显，抬高上限对它们有帮助。但粗粒度与细粒度感知的截断率只有 1.2% 和 4.0%，准确率仍只有 69.6% 和 64.8%。科技类别即使只看正常停止样本也只有 59.26%。这证明还存在模型输出本身、checkpoint/运行时或评分协议方面的差异。

## 7. Judge 差异

论文配置记录的 Judge 是 GPT-OSS-120B，本地冻结 Judge 是 Qwen3.5-4B Base，两者不等价。

- 在 R3 官方式首字母路由下，512 条被首字母规则直接处理，988 条需要 Judge；因此 Judge 替换会明显影响 R3 与论文的接近程度。
- 在 R4 下，1333 条已被可靠地判为明确匹配或明确不匹配，仅 167 条进入 Judge；因此 Judge 不可能解释 R4 中全部 10.53 pp 差距。
- max-token 诊断的 131 次 Judge 调用中出现 3 次非严格 Yes/No 输出。本地与官方 `cal_acc.py` 都只把 `strip().lower() == "yes"` 计为正确，所以这些长回复会被计错。这是 4B Judge 指令遵循不稳定的直接证据，但数量不足以单独改变结论。

若目标是复现论文数值，最高价值的下一项实验不是继续提高 token，而是使用论文 Judge 重算一个独立的“官方协议线”。若 GPT-OSS-120B 仍不可用，必须在报告中保留 Judge 替代限制，不能称为精确复现。

## 9. 后续执行顺序

1. 保留 R3、R4 与 max-token 诊断为三个不同含义的冻结结果，不回写或覆盖。
2. 修正文档中的命名：R4 是“修正版内部基准”，R3 是“官方式解析 + 本地 Judge”，两者都不是精确论文复现。
3. 新建独立协议版本，冻结官方仓库 commit、官方解析器、生成上限、Judge、checkpoint revision、vLLM/Transformers 版本和所有文件哈希。
4. 优先获得 GPT-OSS-120B Judge，对已保存的模型输出先做 score-only 重评；这一步可先隔离 Judge 的影响，成本低于重跑视觉推理。
5. 如需严格跟随公开命令，再用官方 `run_eval.sh` 默认生成合同做独立全量推理，并同时输出官方式分数与 R4 修正版分数。
6. 若仍有显著差距，再向论文作者核对 Table 2 的 Base checkpoint revision、实际评测 `MAX_TOKENS`、Judge endpoint/version 和服务后端。

本轮排查不需要 GPU，未启动新的模型服务或推理任务。后续只有在运行 GPT-OSS-120B Judge 或重新生成模型回答时才需要 GPU/API 资源。

## 10. 项目核心论证记录

本项目将以下判断登记为强工作假设：**作者公开评测器的首字母解析偏差，以及本地与公开生成上限的差异，在量级上足以解释论文 MMStar Base 报告值与本地 R4 修正版之间的表面差距；因此不能把全部 10.53 pp 直接归因于本地模型能力下降。**
