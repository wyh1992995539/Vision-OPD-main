## 1. 项目名称

Vision-OPD 核心机制实现与小规模验证

## 2. 项目目标

本项目计划在有限算力条件下，对 Vision-OPD 的核心方法进行小规模复现与实验验证。

项目将基于官方代码和公开数据，跑通以下核心训练链路：

1. Student 模型根据完整图像生成 on-policy 回答前缀；
2. Teacher 在相同回答前缀下接收包含目标区域的裁剪图像；
3. Teacher 为回答位置提供 token 级概率分布；
4. 使用 top-k JSD/KL 蒸馏损失更新 Student；
5. 使 Student 在最终推理时仅输入完整图像，也能更好地识别局部细节。

本项目的核心研究问题是：

在基础模型、训练数据、训练步数和评测设置基本一致的条件下，Student 自身生成的 on-policy 前缀，是否比固定或预生成的 off-policy 前缀更有利于将局部裁剪图中的细粒度视觉能力迁移到全图模型？

为回答该问题，项目将完成以下工作：

- 建立基础模型全图推理基线；
- 测量模型使用裁剪图像时的细粒度识别能力；
- 完成 off-policy 蒸馏对照实验；
- 完成 on-policy Vision-OPD 主实验；
- 对比训练前后以及 on-policy/off-policy 条件下的准确率、蒸馏损失、显存和运行效率；
- 整理典型成功案例与失败案例，分析方法有效和失效的原因；
- 保存数据版本、训练配置、日志、checkpoint、评测结果和复现命令。

本项目的目标成果是形成一项具有完整证据链的小规模复现实验，包括核心机制实现、基线比较、关键消融、定量评测、错误分析和可复现记录。

本项目不以完整复现论文全部训练规模和全部 benchmark 为目标，也不预先承诺达到论文报告的绝对指标。最终项目结论和成果表述将以实际完成的实验及其证据为准。

## 3. 当前成果定位

当前定位为：

“Vision-OPD 核心机制实现与验证”。

暂不称为：

- 完整论文复现；
- 论文指标复现；
- 独立提出的新算法；
- 完整的大规模训练项目。

只有完成基线、核心训练、on/off-policy 消融、固定评测和错误分析后，
才可以称为“小规模复现”。

## 4. 核心研究问题

在基础模型、训练数据、训练步数和评测设置基本一致时：

Student 自己生成的 on-policy 前缀，
是否比固定或预生成的 off-policy 前缀，
更有利于把局部裁剪图中的细粒度视觉能力迁移到全图模型？

## 5. 实验矩阵

### E0：全图基础模型

- 输入：完整图像
- 是否训练：否
- 作用：记录原始全图能力

### E1：裁剪图诊断实验

- 输入：包含目标区域的裁剪图像
- 是否训练：否
- 作用：判断模型是否具备局部识别能力
- 注意：它是特权信息诊断，不是最终部署方法

### E2：off-policy 蒸馏

- Student 前缀：提前生成或固定
- Teacher 图像：局部裁剪图
- 作用：作为核心对照组

### E3：on-policy Vision-OPD

- Student 前缀：由当前 Student 在线采样
- Teacher 图像：局部裁剪图
- 作用：验证 Vision-OPD 核心机制

## 6. 控制变量

E2 和 E3 尽量保持以下设置一致：

- 相同基础模型；
- 相同训练数据；
- 相同训练样本数量；
- 相同训练步数或训练 token 数；
- 相同随机种子；
- 相同学习率；
- 相同生成参数；
- 相同评测样本；
- 相同蒸馏损失设置。

核心变量只保留：

“Student 前缀来自 off-policy 还是 on-policy”。

## 7. 主要指标

必须记录：

- 全图准确率；
- 裁剪图准确率；
- 训练前后全图准确率变化；
- on-policy 与 off-policy 的准确率差异；
- JSD/KL loss；
- 有效蒸馏 token 数；
- 单步运行时间；
- GPU 峰值显存；
- 输出长度；
- 通用视觉能力是否下降；
- 不少于 20 个错误案例。

- 当前检查结论只覆盖单卡环境，不包含双卡 NCCL/FSDP 通信验证；
- 环境检查原始终端输出尚未归档到本地项目，正式实验启动前应将其保存到实验记录中。

AutoDL 云服务器（后续目标上限）：

- 单节点 2 张 RTX PRO 6000，每张 96GB 显存，总显存 192GB；
- 每张 GPU 分配 22 核 Intel Xeon Platinum 8470Q 与 110GB 内存；
- 双卡实例合计约 44 核 CPU 与 220GB 内存；
- 项目继续使用 CUDA 12.8 路线；双卡阶段仍须单独验证 `torch.cuda.device_count()==2`、NCCL 和 FSDP；
- 系统盘 30GB，不存放 Conda 环境、模型、数据、编译缓存或 checkpoint；
- 数据盘默认 50GB，平台显示可再扩容 206GB；目标扩容到总计 150～200GB，若控制台容量口径不同则以实际可用空间为准。

训练与存储约束：

- 先用单卡完成端到端冒烟，再在相同 global batch 下完成双卡 FSDP 冒烟和效率对比；
- 主实验使用 64 条起步，稳定后扩到 128～256 条，不下载和训练完整 6,241 条数据；
- 当前单卡冒烟使用 `TRAINER_N_GPUS_PER_NODE=1`、`TRAINER_NNODES=1`，rollout tensor parallel 保持为 1；
- 切换双卡后才使用 `TRAINER_N_GPUS_PER_NODE=2`，并在相同 global batch 下重新验证；
- Conda、Hugging Face、Torch、pip、临时文件、rollout 和 checkpoint 统一放到数据盘；
- 最多保留一个包含 optimizer 的恢复 checkpoint，以及一个最终 model-only 结果；
- 双卡资源用于验证 FSDP 分片、NCCL/Ray 稳定性以及单卡/双卡显存和吞吐差异，不视为论文原始硬件复现。

执行路线：

- 本地：读论文、读代码、检查数据、编写配置、分析结果；
- Linux 云 GPU：安装正式环境、模型推理、单卡基线、双卡 FSDP、小规模训练和受控实验。

### 8.1 服务器目录冻结

服务器统一使用以下目录边界：

```text
/root/autodl-tmp/vision-opd/       # 项目代码
/root/autodl-tmp/envs/vision-opd/  # Python/Conda 环境
/root/autodl-tmp/hf_cache/         # 模型与数据缓存
/root/autodl-tmp/torch_cache/      # Torch 扩展缓存
/root/autodl-tmp/pip_cache/        # pip 缓存
/root/autodl-tmp/tmp/              # 临时与编译文件
/root/autodl-tmp/checkpoints/      # checkpoint 和最终模型
```

`HF_HOME`、`TORCH_HOME`、`PIP_CACHE_DIR` 和 `TMPDIR` 应指向数据盘目录，避免占满 30GB 系统盘。

### 8.2 代码修改规则

- `scripts/run_vision_opd.sh` 保留为官方基线，不直接改成单卡参数；
- 单卡、双卡和主实验分别新增独立启动脚本，例如 `run_smoke_1gpu.sh`、`run_smoke_2gpu.sh` 和 `run_main_2gpu.sh`；
- 本地和服务器不得同时修改同一文件；每次远程修改后必须同步回本地并记录；
- 模型、数据、缓存、完整 checkpoint、Token 和 `auth.json` 不进入源码版本；
- 源码、配置、命令、关键日志摘要、评测结果和 Bad Case 需要归档。
